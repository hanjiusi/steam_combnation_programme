02解释层：标签 IDF 画像（SteamTasteAtlas）

画像侧要回答的问题是：每款游戏、每位用户，可以用什么「标签语言」描述？答案是一套可解释、可复算的 IDF 加权标签体系——它既是推荐结果的解释层，也是第二目标的度量来源。

2.1 输入与规范化

输入为 UCSD 公开历史数据集（Australian Steam users/items + Steam 游戏元数据，2026-10-08 下载），两份 gzip 源文件均记录字节数与 SHA256；使用 ast.literal_eval 安全解析后规范化为 JSONL。关键统计：

2.2 数仓：HDFS + Spark + Hive

规范化的 JSONL 进入本机伪分布式的 Hadoop 3.4.2（WSL2 NameNode + DataNode，单机、replication = 1，fsck 健康），由 Apache Spark 3.5.5 完成清洗 / join / explode / 窗口归一化，落成五张 Parquet 表，并用嵌入式 Hive 2.3.9 / Derby 持久化元数据（非独立 HiveServer2）。

2.3 画像口径：IDF 加权与群体对照

IDF(t) = 1 + ln( (N + 1) / (df(t) + 1) )      N = 31,970（背景游戏总数）；df(t) = 标签出现频次
  • 两档权重模式：均衡模式按 ln(1 + 游玩小时) 分配行为质量；时长模式直接按小时——应用于推荐卡证据展示；
  • 游戏内归一化：标签先做 IDF 调整、再在同一款游戏内部归一，保证总贡献不随标签数量膨胀；历史库未收录的新标签取中性 IDF = 1；
  • 用户侧口径：同一用户各标签 share 总和恒为 1（可核对），score 以最强标签为 100；
  • 群体对照：分母为全部 70,912 位有行为记录的历史用户（未出现标签按零贡献），另存 67,894 位有效画像用户的均值与「仅在标签暴露用户中」的条件分位数——界面上三种口径不混用；
  • 边界声明：历史样本有地区 / 时间 / 可见性限制，不代表今天全体 Steam 用户；新旧标签未自动合并；元数据含少量非游戏条目。

2.4 画像服务与流式链路

  • 个人画像：输入 Steam ID64 或主页链接 → 抓取当前可见游戏库（中文名优先）+ 公开商店元数据 → 生成个人画像；历史库为缺失元数据兜底；快照持久化后可离线回看；
  • 双引擎：Node.js 参考实现（与 Spark 口径核对），可选 Spark local[2] 加速；
  • 流式更新：累计时长快照事件（eventId / observedAt / 用户 / 游戏 / 分钟 / 标签）经 Kafka 解耦 → Flink 按用户过滤历史日志并重建状态（增量差分）→ Kafka → Redis 物化查询（按用户合并最新 revision、记录确认消费 offset，结果未变则拒绝重复写入）；
  • 实测：账号 HTTP 端到端更新 36.255 秒（其中 Spark 13.17 秒、流链路 17.248 秒）；Redis 查询抽样核对 260 个标签，最大误差 7.1e-15；
  • 可复查：Parquet 回读行数与画像字段 xxhash64 求和一致（概率性内容校验）；三位历史用户经独立 Python 核对，最大 rawScore 误差 8.88e-15；Node 参考口径与 Spark 结果做 Parquet 双向 exceptAll。

示例账号快照（2026-10 快照）：147 款游戏、104 款有时长、累计 1,647.8 小时、146 款带标签、时长标签覆盖 100%。

03决策层：NSGA-II 多目标推荐（bigdata_steam）

推荐侧的问题：在保证「猜得准」的前提下，让推荐列表「推得广」。做法是把多样性做成第二目标，用多目标演化算法一次求出整条权衡前沿，再自动选取膝点。

3.1 数据与建模矩阵

  • 原始评论 779.3 万条（1.24 GB） → 6 步清洗 → 95.4 万条交互对；
  • 建模矩阵：112,707 用户 × 6,489 款游戏，非零元 731,205 条（密度 0.100%）；
  • 特征：ALS 隐向量 128 维（隐式反馈）；标签侧为 STA 知识库的 337 种标签矩阵（6,489 × 337）；
  • 评估：留一法（test_pairs.parquet），每用户在同一 top-300 候选池内比较，训练集交互在打分时置 −inf。

3.2 指标口径（两把尺子）

RelDCG@10 = mean( rel / log2( rank + 1 ) )          猜得准：训练交互置 −inf、min-max 归一后按位次折损
ILD@10    = 1 − 2·triu(Vn·Vnᵀ,1).sum() / (K·(K−1))  推得广：列表内两两平均距离（行向量 L2 归一）
第二目标   = (1 − w)·ALS-ILD + w·TAG-ILD              w 为唯一的模式变量（0 ~ 1 五档）
膝点       = argmax( RelDCG × ILD )                  准确度 × 多样性乘积最大的点
等准确度门槛 ρ = 0.90                                 各模式允许的准确度 ≥ 该用户 ALS Top-10 的 90%

3.3 实验设置（全程锁定）与优化管线

统一设置（可复现）

  • 40 个演示用户：带固定随机种子的可复现抽样；
  • 候选池：ALS 全域打分后逐用户截取 top-300；
  • 演化参数：种群 150 × 60 代，全部实验一致；
  • 随机种子：42（全局统一）；
  • 唯一变量：相似度来源 w = 0 / 0.25 / 0.50 / 0.75 / 1。

NSGA-II 管线

  • ALS 128 维隐向量 → 全域打分 → 每用户 top-300 候选池；
  • 非支配排序 + 拥挤度保持，迭代 60 代；
  • 一次运行得到整条帕累托前沿（五模式 1,476 ~ 2,582 个非支配解）；
  • 膝点自动选取（argmax RelDCG × ILD），无需人工调档；
  • 对照组：MMR 重排（α = 0.3 / 0.5 / 0.7）与纯 ALS 基线。

05融合层：复算、校验与演示站（combination）

融合侧的工作原则是「不重跑实验、但逐位复核」：从 BDS 的实验产物复算出前端所需的全部数据快照（web-data），并做三重校验后固化；页面数字与源实验逐位一致，稳定可复现。

5.1 web-data：前端数据快照

  • meta.json：群体指标、5 模式膝点与 ρ=0.90 增益、对照实验、16 项源文件 SHA256 指纹；
  • users.json / items.json：40 位演示用户（画像 top 标签与案例标注）与 6,489 款游戏（名称 + 标签索引，100% 名称覆盖）；
  • reco/<uid>.json ×40：每位用户 × 5 模式的完整推荐列表、帕累托前沿点、膝点与 ALS 基线对照。

5.2 三重校验（构建时逐项执行）

① 膝点复算

膝点均值与源实验 sim_w_sweep.json 逐位一致（差 0.00e+00）；第二目标逐点复算最大偏差 5e-06。

② 基线对照

ALS Top-10 指标与 BDS 记录差 ≤ 5e-05（浮点显示级）。

③ 覆盖率

6,489 / 6,489 款游戏名称 100% 覆盖；标签库命中 100%。

  • 画像页 /：标签图谱（圆面积 ∝ score，点击节点查游戏证据）、证据面板、时长图（条形 ∝ 小时）、快照离线回看；

07局限与展望

诚实边界

  • 画像侧：单机伪分布式（replication 1），非多节点集群、不构成容灾承诺；历史下载数据有地区 / 时间 / 可见性限制，不代表当前 Steam 人口；新旧标签未自动合并；元数据含少量非游戏条目；
  • 推荐侧：结论基于 40 个演示用户与单一随机种子（42），未做多种子重复与显著性检验；ILD 是「列表内两两平均」的代理指标，指标改善不等于体验改善；
  • 案例层：个体收益因人而异（A 让 7.1% 准确度、C 让 3.7%、B 保命中）——群体结论稳定，个案只是注脚。

下一步计划

  • 补多种子重复实验与显著性检验，给出置信区间而非单点均值；
  • 从 40 个演示用户扩展到全量 11.2 万用户验证规模稳定性；
  • 引入第三个优化目标（如新颖性 / 覆盖率），观察三维前沿；
  • 画像侧持续推进流式链路与增量快照的长期运行验证。
